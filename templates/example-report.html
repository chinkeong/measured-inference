Qwen 3.8 27B Optimal settings

How to run Qwen3.8-27B well on whatever you have — RTX 30/40/50 series, DGX Spark (GB10), Intel Arc Pro B50/B70, or an Intel Arc B390-class iGPU. Grounded in measured runs on an RTX 3090 and fact-checked against published specs and community benchmarks.

01

The model, in five facts that drive every setting

  • Hybrid attention. Most of its 64 layers use Gated DeltaNet, a linear-attention design whose memory use stays constant no matter how long the context gets; only 16 of the 64 are standard attention layers (and those use GQA with 4 KV heads). The result: KV costs just 64 KiB per token at fp16 — 4.0 GiB at 122k context with a Q8 cache, 7.5 GiB unquantized — where a dense 27B storing KV in every layer would need exactly 4× as much. Huge contexts are cheap in memory, and speed falls off gently as they fill rather than collapsing.
  • Native 262,144 context. No YaRN or rope tricks needed below that; the limit you'll actually hit is VRAM, not the model. (The model card lists extension to 1M via YaRN — out of scope here: the KV cache alone would run ~34 GiB even at q8_0.)
  • Thinking always on, defaulting to xhigh. Reasoning tokens share the context window with your prompt and output — a 100k-token thinking run needs a >100k window (§04).
  • Vision is optional at serve time — and it costs context. The BF16 mmproj projector takes ~0.9 GB of VRAM, which at a Q8 cache is ~27k tokens of window (§02's arithmetic). Serving text-only converts vision you aren't using directly into context: it's what lets UD-IQ4_XS hold the full native 262,144 on a 24 GB card (§08 Choice B prints both variants).
  • Official thinking-mode sampling: temp 1.0 · top-p 0.95 · top-k 20 · min-p 0. Clients that silently send temperature 0 (aider does) cause repetition loops — override them.

02

The physics: bandwidth is king, and VRAM is a cliff

Generation speed comes down to one ratio: how fast your card can read memory, divided by how much it must read per token. Every token requires reading the entire model — about 16.5 GB for a 4-bit quant. So take your card's bandwidth in GB/s, divide by 16.5, multiply by ~0.7 (the efficiency we measured on CUDA), and that's your speed ceiling in tokens per second. This one calculation predicts every row of the matrix in §07.

The second law: speed vs. context is a cliff, not a curve. Flat while weights + KV fit in VRAM; a collapse once anything spills over the PCIe bus — and the magnitude scales with how much spills: ~10× when the weights file itself lands in system memory (the 256k point below), a measured 1.5–2× from even a ~2 GB spill (§10). Corollary

Allocated is not the same as used: a big context window with a small prompt in it costs VRAM, not speed. And as long as you stay below the cliff, shrinking the window gains you nothing — there is no hidden "optimal point" to search for.

That corollary now has a measured face. Probed 2026-08-22 with Q4_K_M (q8_0 KV, MTP on, mmproj loaded — the ~1 GiB-larger UD-Q4_K_XL shifts every ceiling ~30k tokens lower, while dropping --mmproj frees ~0.9 GiB and raises them ~27k, to roughly ~158k fully resident) by stepping -c upward with short temp-0 decode probes: speed holds at ~50–55 t/s all the way to -c 212992, turns borderline at 217,088 (41.2 t/s), and collapses at 221,184 (19.5 t/s). But nvidia-smi tells the other half of the story: dedicated VRAM hits its ~24 GB ceiling already at -c 131072 (measured 24,052 MiB) — past that point the KV cache is overcommitted, and the run stays fast only while a short prompt leaves the deep pages untouched. So a 24 GB card has two ceilings, not one: ~131k is the practical fully-resident ceiling — fast even when a long run actually fills it, though it sits right at the margin (the recipe's 122,880 deliberately leaves headroom below it), and it is the same number the budget table's arithmetic lands on below — while up to ~213k loads and runs fine for shallow use, degrading progressively as real tokens land in the overcommitted tail.

Two footnotes the table earns. First, the q4_0-KV flag: the problem is not that quantization error "accumulates" — each cache entry is quantized once — it's that at long context every new token attends over hundreds of thousands of perturbed entries, and retrieval gets flaky at exactly the 200k+ lengths a q4_0 cache would enable. q8_0 is the deepest safe cut. Second, prefill: these budgets make a 200k+ prompt fit, but filling it is quadratic work on the 16 full-attention layers — a genuinely full 100k prompt takes several minutes to first token on a 3090, potentially tens of minutes at full 200k+ (an estimate, not a benchmark; the reference run's ~2k prompt hides this cost entirely).

03

Universal rules — true on every card

  • One token pool. prompt + thinking + output ≤ context. The model has no awareness of its limits and cannot budget its own thinking; limits are enforced by your config only.
  • Cut-offs are client-side. The server generates until told to stop. Truncations come from the client's max_tokens, its request timeout, or Ctrl+C — and with OpenAI-compatible APIs a cut generation cannot seamlessly resume. Size max_tokens and the client timeout so the whole run fits one response.
  • One slot, quantized KV. --parallel 1 (some UIs default to 2 = double KV) and -ctk q8_0 -ctv q8_0 (halves KV, negligible loss — but never q4_0 for the KV cache; why: §02).
  • --load-mode none — harmless everywhere, essential on RAM-tight machines; every §08 recipe ships it by default (replaces the deprecated --no-mmap). Without it the whole GGUF stays cached in system RAM even after the weights are in VRAM — ~15 GB freed for the Q4 file. The cost is a slower model load: measured ~10–30 s to first health check across tonight's dozens of restarts (SSD-dependent).
  • -ctk q8_0 -ctv q8_0 — now verified, not assumed. Measured wikitext perplexity with the Q8 cache: 6.5498 vs 6.5348 at fp16 — +0.23%, inside the error bars. Half the KV VRAM for statistically nothing. (Avoid q4_0 for K at long context — §05's mechanism note.)
  • --parallel 1 — also measured. Two concurrent requests at --parallel 2 gained only +11% aggregate throughput (79.2 vs 71.3 t/s) while making each request ~40% slower and halving the per-slot window. For one user — even one driving multiple agents — queueing beats sharing.
  • All layers on GPU or accept the cliff. Partial offload speed is set by CPU RAM bandwidth, not by the GPU — a 5080 and a 4060 Ti offload at nearly the same ~8–12 t/s (assuming two sticks of DDR5 in dual channel, ~90 GB/s; a single stick halves the bandwidth and the t/s with it). And this is a dense model: the MoE escape hatch of parking expert tensors on CPU (-ot) has nothing to target here, so every offloaded layer sits on the critical path of every token. (Two ways this rule silently breaks: §10.)

Rule of thumb

For a benchmark, use the same quant on every machine (Q4-class) — a different quant is a different model and its scores aren't comparable. For daily use, pick the best quant that fits entirely in your VRAM.

Does FP4 beat INT4? A scored smoke test

First, what the two formats actually are. A 4-bit quant stores each weight as one of only 16 allowed values — the formats differ in where those 16 values sit:

A common belief says floating-point formats always beat integer formats at the same bit width. We tested it: the three quants above, graded for correctness on GSM8K and MATH-500 (20 problems each, greedy decoding, identical prompts, 4096-token budget; answers that ran out of budget mid-thinking count as wrong and are reported as truncations). One framing rule before the numbers: at 20 problems this is a smoke test, not a ranking. (Throughout this guide a point means a percentage point of accuracy — 94% → 95% is one point. It is an absolute unit, unlike "percent better", which is relative; and in a scored run, points and questions are chained together: at n=20 each question is worth 5 points, at n=200 each is worth 0.5.) The smoke test's job is to catch a broken quant — a bad conversion or mangled chat template collapses a score by 20–40+ points, which even n=20 detects reliably. It cannot rank healthy quants, whose true gaps are a point or three (the arithmetic is in §09). What the numbers say:

  • "Floating point always wins" did not survive the test. All three tied on GSM8K; on MATH-500 the integer-grid K-quant answered two more problems than either FP4 file. At 20 samples that edge is weak evidence — but it is the opposite direction from the belief. What actually decides 4-bit quality is how cleverly a format spends its bits — block sizes, scale precision, which layers stay high-precision — and mature K-quants are very good at that game. Both families use fine-grained scaling; the float-vs-integer grid underneath matters far less than people assume.
  • The two NVFP4 tiers were indistinguishable at this sample size — which is expected under noise, not evidence of equivalence. The file structure does predict a tie, though: the family shares one byte-identical NVFP4 backbone, with tiers differing only in the surrounding layers. The surprise is where VERY-LOW's savings actually landed: on these math prompts at n-max 10 its MTP draft head drafted noticeably worse (acceptance length 3.33 vs ~4.8) — a speculative-decoding speed cost, not an accuracy one. The penalty is config-dependent, though (n-max and p-min are the speculation knobs §06 tunes): re-measured 2026-08-22 at the tuned n-max 4 / p-min 0.75 on code generation, both tiers accepted identically (0.83) and VERY-LOW was the faster file (54.6 vs 48.2 t/s) — smaller weights, less memory traffic per token.
  • Sample-size honesty: each problem is worth 5 points. Every gap in this table is one or two questions wide. Treat it as "no meaningful quality difference, mild edge to the K-quant" — not a ranking. We also ran the same prompts through a different serving stack and grader version and saw individual cells move by up to 10 points, which means measurement variance is the same size as the differences being measured. Anyone showing you a one-run quant ranking without error bars is selling something. §09 puts numbers on exactly how underpowered a 20-question run is.
The takeaway

Pick your file by size and speed, not by format ideology: on a 24 GB Ampere card that means Q4_K_M or the smaller UD-IQ4_XS. Q4_K_M is the fastest of the three files smoke-tested here (best-drafting MTP head — the n=20 smoke test found nothing against it, and the measured wikitext perplexity below comes out in its favor); the dark-horse callout below splits it against UD-IQ4_XS. NVFP4's real advantages live on Blackwell hardware where the format runs natively.

Accuracy at 20 questions cannot separate healthy quant files (§09 carries the full arithmetic) — but per-token metrics can. Perplexity here is the classic model-quality metric, not the search engine (which named itself after it): run the model over real text and score how well it predicted each actual next token. A perplexity of 6.5 means that at every step the model was, on average, as uncertain as choosing between ~6.5 equally likely words — perfect prediction would be 1, and lower is better. Because quantization damage makes prediction slightly worse everywhere, this metric feels it at all ~330k token positions instead of collecting one right/wrong bit per benchmark question. The dark horse: UD-IQ4_XS

The table's second row is the night's discovery. At 13.3 GiB — 2.1 GiB smaller than Q4_K_M — UD-IQ4_XS ties it on quality (perplexity within ~1σ, GSM8K within noise) and, because decode is bandwidth-bound, the smaller file is faster everywhere it was measured: prefill 1365 vs 1303 t/s, plain decode 43.8 vs 39.9, GSM8K with speculation 73 vs 63. The saved VRAM becomes context: its measured fully-resident ceiling with the vision projector loaded is ~180–190k (vs Q4_K_M's ~131k), shallow probes stayed at 65–70 t/s all the way to the full native 262,144 with no collapse anywhere (pre-re-sweep flags at the larger -c allocations — the tuned-MTP near-empty measure on the 196k config is 79.3–79.9 t/s, §08's menu), and by §02's arithmetic a text-only launch (no mmproj) holds the entire native context fully resident — the capability this guide previously reserved for 3-bit files, now at Q4-class quality (a headless/bare-desktop configuration: its ~1 GiB slack does not survive a browser — §08's Choice B ships the desktop-safe 196k instead). Why still name Q4_K_M the default? Two defaults, two scopes: Q4_K_M is this guide's measurement base and maximum-quality pick — both quality metrics lean the same whisker in its favor, it is the file every number in this guide was measured on, and IQ-format decode support varies more across backends (measured on CUDA) — while UD-IQ4_XS at -c 196608 is the reference machine's shipped daily default (§08's launcher menu, row [1]). Context- or speed-hungry: pick UD-IQ4_XS. Maximum measured quality at 122k: stay on Q4_K_M. Either is right.

MTP speculative decoding — free speed on every GPU

Qwen3.8-27B ships with a built-in multi-token prediction (MTP) draft head — a small helper network that guesses several tokens ahead so the full model only has to check them, which is much faster than generating each one. The standard K-quant GGUFs (§05's table) already include it (the head itself always stays at 8-bit, whatever the main quant). llama.cpp added support in July 2026, and because every guess is verified by the full model before it's accepted, the output is exactly what the model would have written anyway — you only gain speed. It works on any GPU llama.cpp supports: Ampere, Ada, Blackwell, Arc, iGPUs.

  --spec-type draft-mtp  --spec-draft-n-max 4  --spec-draft-p-min 0.75

How much speed it adds depends heavily on hardware and workload — reports range from +33% to +145%. An RTX 5090 tester saw 148 avg / 203 peak t/s on the NVFP4 tiers. On our reference 3090, generation went from 40.3 (the 08-21 build's cold-start baseline; the canonical 08-22 baseline is 39.7–39.9) to 58–60 t/s — +45% at the default-ish settings (n-max 4, 89% of drafted tokens accepted) — and on the original benchmark prompt, tuning pushed it to 81.7 t/s, +105% (n-max 10, p-min 0.5) — though a 2026-08-22 re-sweep on realistic code inverted that ranking in favor of n-max 4 / p-min 0.75 (the full story, and the mechanism behind the flip, is in the sweep section below). The warning all these numbers carry: benchmark on your own machine. That 5090 tester found n-max 4 fastest with 6–8 slower; our 3090 agreed on real code yet kept climbing to n-max 10 on its near-ideal prompt — the optimum moves with hardware and content, so there is no universal best value. You'll need a llama.cpp build recent enough to have the draft-mtp feature.

One more measured nuance before you pencil 82 t/s into your plans: the speedup is set by draft acceptance, and acceptance is set by your content. The head only wins when its guesses match what the full model was about to write — easy for boilerplate and predictable code, hard for prose that could go anywhere. Acceptance is the speed

The cleanest demonstration we measured (2026-08-22): same card, same flags (n-max 10, p-min 0.5, temp 0), only the content differs. Generating novel code: 51.5 t/s — acceptance 0.47, mean accepted run 4.0 of 10 drafted. Copying a provided snippet verbatim: 119.8 t/s — acceptance 0.93, mean run 9.9 of 10. A 2.3× speed difference with identical settings. Draft acceptance is not a detail of speculative decoding, it is the whole mechanism — which is why a speculative benchmark number quoted without its acceptance rate is unfalsifiable.

DFlash2 — block drafting (PR stage)

DFlash2 drafts differently from MTP: instead of guessing one token at a time, it predicts a whole 7-token block in a single pass, then picks the most plausible sequence out of the candidates it considered for each position. Like MTP, every draft is verified before it's accepted, so the output is identical to running the model alone. The costs: a separate 1.14 GB drafter model to download (incoai/Qwen3.8-27B-DFlash2-GGUF, ~1.2 GB of VRAM), and — until llama.cpp PR 27342 is merged — building llama.cpp yourself from that branch.

Read this section as a case study, not as settings advice: the sweep below was measured carefully, is internally consistent — and its headline conclusion did not survive contact with realistic content. The verdict that did survive is in the re-sweep callout at the end; the sweep itself stays because how a clean benchmark misleads is worth more than another settings table. Three findings, all measured 2026-08-21:

  • On this prompt — and only on prompts that draft like it — the tuned built-in MTP head won outright: n-max 10 with p-min 0.5 gave 81.7 t/s, +105% over baseline, beating DFlash2's best (77.6 at n-max 4–5). No drafter download, no source build, no VRAM cost. (On realistic code the same flags measure 48.3 — the re-sweep below.)
  • --spec-draft-p-min is the hidden second knob. At n-max 10, lowering it from 0.75 to 0.5 was worth +8 t/s (73.5 → 81.7); at n-max 4 the difference was small. A high confidence floor keeps pausing exactly the long drafts that big n-max exists for.
  • DFlash2's recommended n-max 7 was not its own best setting here — 4 and 5 both beat it (77.6/77.5 vs 74.0). Every recommendation in this space, including ours, is one machine's measurement.
The re-sweep — real content flips the verdict

Those findings are one prompt's truth, and that prompt drafted near-ideally. Re-swept 2026-08-22 — 10 configurations, temp-0 code-generation probe — the ranking inverted: n-max 4 / p-min 0.75 won at 57.9 t/s (acceptance 0.81), while the benchmark prompt's champion n-max 10 / p-min 0.5 fell to 48.3. DFlash2 flipped with it: its best on real code was 46.5 t/s (n-max 2) — below tuned MTP, the reverse of its benchmark-prompt 69–77, and a hard sell for the extra download and source build. The mechanism reverses with the acceptance rate: at ~80% acceptance long drafts compound into free tokens; at ~50% they compound into wasted verification, and a high confidence floor is what keeps the drafter honest. So the setting this guide ships — here and in every §08 recipe — is n-max 4 / p-min 0.75, with the chart above kept as measured history and as proof that any single-prompt sweep, ours included, overfits its prompt.

The one curve under all of it

Every MTP number this guide has ever measured sits on a single line: speed as a function of draft acceptance. Novel code at acceptance 0.47 → 51.5 t/s; this sweep's near-ideal benchmark prompt → 81.7; copying text verbatim at 0.93 → 119.8 — all on the same card with the same flags. The old sweep was never wrong as a measurement; it was wrong as a promise, because it reported one point on this curve as if it were the curve. Your content decides where you sit on it; the flags only tune how gracefully you sit there.

Reading acceptance tables

Published speculative-decoding tables (like the DFlash2 blog's "mean acceptance length") are speed numbers, not quality scores. The verify step guarantees every configuration writes exactly what the base model would have written — a higher acceptance number just means more tokens got through per check. Quality only changes when the weights change (a different quant); speed only changes when the drafter changes.

How big must a benchmark sample size be?

A worked example from this guide's own data. A GSM8K score of 85% at 20 questions carries a 95% confidence interval of roughly 64–95% (Wilson) — a thirty-point window around a table where every score sits within ten points of every other. One flipped question moves a score 5 points. Healthy Q4-class quants differ by perhaps 1–3 true points; inside that window, such a gap is invisible. The principle generalizes to any benchmark of any size: the question is never "is n big enough?" in the abstract, but "is n big enough for the gap I need to see?"

The arithmetic is unforgiving because sampling noise shrinks with the square root of the sample count: halve the gap you want to detect and you need four times the samples. What that costs on this 3090 — paired evaluation on the same questions, temp 0, ~80% base accuracy, 95% confidence at 80% power, ~1,200 tokens per sample at ~55 t/s:

True gap to detectSamples neededWall clock per model
~20 pts — a broken quant~25–30~9–11 min
~10 pts~100–150~35–55 min
~5 pts~300–500~2–3 h
1–3 pts — typical Q4 vs Q4~2,000–10,000~12–60 h

The first row is the one job a local accuracy run does well — and the only claim §05's scored smoke test makes. The last row is why nobody ranks healthy quants by accuracy scores: the run that could would take days per model.

The other way a benchmark lies: the token budget

Sample size is not the only silent corrupter. A thinking model spends tokens reasoning before it answers, and a fixed max_tokens cap silently converts its hardest questions into wrong answers — the run doesn't error, the score just drops. Measured here: the §04 effort comparison first ran GSM8K n=200 with a 4,096-token cap, and xhigh scored 94.0% with 5 answers cut off mid-thinking and graded wrong — while low and medium, which think less, never touched the cap. The cap didn't measure the model; it taxed exactly the setting that thinks most, on exactly the questions that need it most.

The tempting fix is the wrong one: "rerun using only the questions that didn't truncate." That selects the question set based on one arm's behavior — dropping precisely the hard items where a quality difference could live — and quietly changes the question from "which setting scores better?" to "which setting scores better on easy questions?" It also breaks comparability with every published number on the same benchmark. The logical fix is to raise the budget, not shrink the test: rerun with a cap the longest thinker cannot hit (16,384 here). And because greedy decoding is deterministic, arms that never truncated produce byte-identical output under any larger cap — only the truncated arm needs rerunning. The corrected number lives in §04's table, capped result beside it in brackets.

The checklist line

Before trusting any thinking-model benchmark score — yours or a leaderboard's — ask two questions: what was max_tokens, and how many answers truncated? A score published without its cap is unfalsifiable, for the same reason a speculative-decoding speedup without its acceptance rate is (§06).

The right tool

KL-divergence and perplexity rank quants; a small-n accuracy pass smoke-tests everything those metrics can't see. Logit-level metrics compare per-token probabilities against the full-precision model over ~330k token positions in an estimated ~15–30 min per model on a 3090-class card (an estimate, not a benchmark from this guide — that covers the per-quant pass against saved full-precision baseline logits; generating the baseline itself needs the BF16 model, which exceeds a 3090's VRAM, and is a slower one-time cost), resolving differences no feasible accuracy run can — which is why quant authors themselves (unsloth's Dynamic 3.0, for example) compare files this way. But they run below the sampling and template layer, so a broken chat template or mangled tool-call format sails through them unnoticed while collapsing scored answers by 20+ points. Run both: KLD to pick between files, one cheap accuracy pass to confirm the file you picked actually works end to end — §05's perplexity table is this advice in practice.

When it silently runs at half speed

Two failure modes produce the same complaint — the command that did 40 t/s yesterday does 25 today — while the server starts cleanly and reports nothing wrong. Both were measured on the reference 3090 (2026-08-22), and both are configuration, not hardware.

Failure 1 · The silent VRAM spill

The NVIDIA driver does not refuse an allocation that exceeds VRAM — by default it quietly overflows into shared system memory across the PCIe bus. On the reference machine, two open browsers held ~2–3 GB of VRAM; the 122,880-context config needed ~22 GiB (§02's budget table); about 1.9 GB spilled. The server loaded without a single warning and decoded at 20–35 t/s — and stayed there no matter how far the context was shrunk, because the weights stay spilled either way. This is §02's cliff in its most treacherous form: the cliff is invisible to the server. Nothing errors, nothing is logged, everything just runs at half its speed or worse.

The signature lives in Task Manager: dedicated GPU memory pinned at 23.5–24.0 / 24.0, shared GPU memory growing, CPU around 70% from driver paging. The fix is freeing the VRAM (close the apps holding it). The prevention is making the failure loud: NVIDIA Control Panel → Manage 3D Settings → Program Settings → llama-server.exe → CUDA — Sysmem Fallback Policy → Prefer No Sysmem Fallback. With that set, an over-budget load fails with an out-of-memory error at startup instead of running slow all day.

Failure 2 · The -ngl off-by-one

llama.cpp counts the output projection as one more "layer" than the model has transformer layers. This model has 64, so -ngl 64 reads as complete — and leaves the output layer, a 5120 × ~151k-vocab matmul that runs for every generated token, on the CPU. Measured cost: decode 25.7 vs 39.7 t/s, prefill 106 vs 290 t/s (server-log prefill on the short test prompt — a different probe from llama-bench pp512, which reads ~1300 on this card), GPU utilization 53–67% instead of ~90%, and a stack of CPU threads pinned doing the vocab matmul. The recipes in §08 all say -ngl 99 for exactly this reason: any number past the real count means "everything", with no off-by-one to get wrong. One log line to read carefully: failed to fit params to free device memory: n_gpu_layers already set by user only means an explicit -ngl overrode the automatic fit — any value triggers it, -ngl 99 included. The Failure-2-specific signals are the ones in the table below.

High CPU alone proves nothing

llama.cpp worker threads busy-spin while waiting on the GPU, so ~50–70% CPU during perfectly healthy all-GPU decode is normal on a 20-thread machine. The trouble signal is the combination — high CPU and low t/s. Either failure above shows both.

The commands that actually work on Windows

One tooling trap cost this guide's own debugging session real time: on Windows, nvidia-smi's per-process listing shows [N/A] or "Insufficient Permissions" for memory, and its memory.used only counts dedicated VRAM — it cannot see the spill. The tools that exposed both failure modes:

nvidia-smi --query-gpu=memory.used,memory.total,utilization.gpu --format=csv

(Get-Counter '\GPU Process Memory(*)\Shared Usage').CounterSamples |
  Measure-Object CookedValue -Sum   # divide Sum by 1MB; growing = spilling

# per-process dedicated commitment - this is what caught the compositor (dwm)
# holding 3.6 GiB during a browser-UI session:
(Get-Counter '\GPU Process Memory(*)\Dedicated Usage').CounterSamples |
  Where-Object { $_.CookedValue -gt 200MB }

When 27B is enough — and when the frontier earns its keep

A closing dose of perspective — with a disclosure up front: unlike everything above, this section is argued from the published literature, not measured on this machine. The question it answers is the one every local-inference guide dodges: which tasks should you trust this machine with? A model does not need trillions of parameters to act as an encyclopedia. High-frequency knowledge — geography, mainstream history, standard biology, common coding syntax — compresses comfortably into 27B (a model stores on the order of 2 bits of factual knowledge per parameter), which is why local factual Q&A feels frontier-grade. What frontier models buy with their scale looks like a difference in kind but is built from differences in degree: per-step reliability improves smoothly with capability, and because a long task succeeds only if every step does, those smooth gains compound into cliff-like gaps on exactly the work below — as reasoning engines, software architects, and autonomous agents. The boundary runs through five territories:

  • Long-horizon reasoning. Direct questions are effortless at 27B; what degrades is the 30-step deduction, the formal proof, the architecture analysis — work where one early flaw silently poisons everything downstream: agent success decays exponentially with task length, and transformers solve deep compositional problems by pattern-matching that collapses as the reasoning graph grows — a collapse that reaches even frontier models at sufficient depth, so the frontier extends the horizon rather than escaping the regime. This guide's §04 judging located the local edge precisely: at xhigh, the 27B delivered 100% of a complex single-file spec, twice. Multi-file systems, where the flaws hide in the seams between files, are where the footing gives.
  • The long tail of knowledge. 27B keeps what training data repeated often — fact recall tracks how many times a fact appeared in pre-training — and frontier models retain far more of the rare: the niche legal precedent, the legacy framework, the unusual drug interaction (the studies measure trivia-style entity facts; these are the practical analogue). But the tail deficit shrinks rather than disappears — scaling fails to appreciably improve memorization of tail facts, and closing the gap by scale alone would take many orders of magnitude more model. The danger is the failure mode: on obscure ground no model reliably says "I don't know" — training and benchmarks reward confident guessing over abstention — and a small model simply has more gaps for the fluent hallucination to fill. Treat confident answers about rare domains as unverified drafts, or ground them with retrieval: retrieval-augmented small models beat vanilla models orders of magnitude larger on exactly these facts.
  • Ultra-long recall. A whole codebase or a 500-page audit in one prompt is two problems wearing one coat: holding the text, which this card's 122k window does (§02), and keeping every cross-document dependency straight, which improves with model scale — in RULER's within-family test, a 34B degrades far less than a 6B trained on the same context — but scale mitigates rather than cures: only about half of models claiming ≥32K actually handle 32K, information buried mid-context is used far worse than at the edges, and once retrieval requires inference instead of literal matching, most long-context models fall below half their short-context accuracy by 32K.
  • Multi-constraint instruction following. "Five custom API rules, strict typing, an exact JSON schema, and ten edge-case tests — simultaneously." Rule stacks like that degrade small models first, and quietly: the dominant failure at high instruction density is silent omission — the output stays a coherent, compliant-looking document — and violations are hard enough to spot that benchmarks need LLM judges to find them. Every model declines as constraints stack, so fidelity under heavy constraints is one of the clearest capability dividends — frontier reasoning models hold near-perfect through ~150 simultaneous instructions where small models decay exponentially — but it buys later, slower degradation, not immunity: even the best fall to ~68% at 500 instructions.
  • Autonomous agentic reliability. An agent that calls tools, reads its own error logs, and self-corrects across dozens of steps multiplies its per-step error rate through every step — measured agent success declines exponentially with task length, like a half-life — and worse than independent errors predict, because models self-condition on their own earlier mistakes, amplifying drift into failure. Frontier agents push the horizon from minutes toward hours, but at 50% success — at their quoted horizon they still fail half the time. This is why the setups in the next section shine for supervised sessions — every model is near-perfect on short, checked steps — and wobble on multi-hour autonomous loops, and why §04's defect cliff matters most in exactly this mode, where nobody is watching the output.

The honest division of labor

A well-tuned local 27B is a fast, private, tireless colleague for the bounded work that fills most of a day — and this guide exists to make it as good at that as the hardware allows. Frontier models exist for the multi-step, high-stakes cognitive work where accuracy must decay as slowly as possible — and even they decay. Step 4 · Fix aider's defaults for a thinking model

Aider sends temperature 0 by default — a repetition-loop trigger on reasoning models — and needs to know to strip <think> blocks before parsing edits. Create .aider.model.settings.yml next to the metadata file:

- name: openai/qwen/qwen3.8-27b
  use_temperature: 1.0
  reasoning_tag: think
  extra_params:
    top_p: 0.95

Step 5 · Launch

aider --model openai/qwen/qwen3.8-27b --edit-format diff --timeout 3600
  • --edit-format diff — the model writes only changed hunks instead of whole files. On local t/s this is the biggest quality-of-life setting there is: a 60 KB file edit drops from minutes to seconds. Diff also degrades gracefully on cut-offs (complete hunks still apply).
  • --timeout 3600 — long thinking runs outlive default client timeouts; the server log shows a timeout as "Client disconnected. Stopping generation".
  • First run sanity checks: the model-warning banner should be gone (metadata file found), and the banner should read diff edit format. If edits arrive mangled, the fallback is removing --edit-format diff to use whole-file mode.
  • Vision: with supports_vision: true and the server launched with --mmproj, you can /add screenshot.png in aider and the local model will see it.

# BOTH blocks are required: registering the provider is not enough — without the
# routing block the harness silently keeps its cloud default and fails with

agent-default-model:

llm-pi-ai:

    llamacpp:

        supportsDeveloperRole: false  # llama-server wants a plain system role

      models:
        - id: qwen/qwen3.8-27b
          input: [text, image]        # vision works when the server runs with --mmproj
          contextWindow: 122880       # match the server's -c value
          maxTokens: 106496           # REQUIRED: dsh enforces this client-side (same Pi
                                      # schema). Without it the small default cap cuts long
                                      # thinking replies mid-run — the symptom is "Output token
                                      # limit reached … send continue" on any xhigh answer (§03)

The harness's headline trick is routing: it plans with heavy reasoning, then fans the plan out to sub-agents that execute with light reasoning. Two things to know when backing it with llama-server. First, llama-server ignores a per-request reasoning_effort field (same dialect issue as Pi above) — effort is fixed server-side via --chat-template-kwargs, so either run one server at xhigh (this guide's quality-first default), or run two llama-server instances (one xhigh planner on one port, one low executor on another) and register both as separate models in settings.yaml — the harness can then route between them. Second, its parallel sub-agents each hold their own context: with --parallel 1 (this guide's recipes) requests queue rather than run concurrently, which is correct on a single 24 GB card — raising --parallel multiplies KV cache and walks you off the §02 cliff. For non-thinking "fast mode" runs, Qwen's official instruct sampling is temp 0.7 · top-p 0.8 · presence penalty 1.5.

One rule for all agents

Whatever the agent, its context and max-output settings must match the server's -c value — the client-side limits are what prevent the silent mid-generation cut-offs, because the model itself cannot budget its own tokens (§03).

01The model

Seven facts that decide every flag you will type.

Qwen3.8-27B is not a plain transformer, and almost every surprising number further down this page traces back to that. Its 64 layers repeat a four-layer block: three Gated-DeltaNet linear-attention layers, then one gated full attention layer. (CITED — model card: “16 × (3 × (Gated DeltaNet → FFN) → 1 × (Gated Attention → FFN))”; confirmed against the layer_types array in the base repo's config.json, fetched during this run.)

Architecture — 16 of 64 layers keep a KV cache

01Only 16 layers pay rent per token

Cache arithmetic counts full-attention layers only: 2 × layers × n_kv_heads × head_dim × bytes. With 16 full-attention layers, 4 KV heads and a 256-wide head, that is 65,536 B/token at fp16 and 32,768 B/token at q8_0 nominal — 34,816 B once q8_0's per-block fp16 scale is counted. DERIVED from the fetched config.json.

02The other 48 layers are free as the window grows

Each Gated-DeltaNet layer holds a fixed recurrent state (48 × 128 × 128 fp32) plus a 4-tap convolution state — 3.16 MiB per layer, ~151 MiB for all 48, no matter how long the context is. DERIVED. This is the entire reason a 27B model can hold a 262k window on a 24 GiB consumer card.

03A window token really costs 44 KiB, not 34

MEASURED: stepping -c from 32,768 to 163,840 moved llama-server's dedicated VRAM in exact 1,408 MiB steps per 32,768 tokens — 45,056 B per token of window with the MTP drafter on. (The projector was loaded for that sweep too, but it is a fixed cost, not a per-token one, so it does not enter the slope.) Budget with the measured figure, not the arithmetic one: the arithmetic is a floor.

A control pair with --spec-type none at the same two contexts splits that figure: 39,936 B/token for the cache alone, and 5,120 B/token more once the MTP drafter is on, because the draft path keeps its own cache. MEASURED. The full bill for speculation is 1,008 MiB fixed plus 5,120 B per window token — 1,808 MiB at a 163,840-token setting — and a further 898 MiB if you raise the draft depth from 4 to the 10 the coding recipe ships.

04The speculative drafter is inside the file

The GGUF carries a trained multi-token-prediction head as blk.64.nextn.*. With --spec-type none the server logs model has unused tensor blk.64.* -- ignoring and skips it; turn it on and, writing a JavaScript class at -c 32768 and temp 0, you get 2.26× decode — 42.17 to 95.35 t/s of answer tokens — for about 335 MiB of weights DERIVED from the tensor byte sizes the server printed while ignoring them. No companion draft model is needed or wanted.

05Thinking depth is a load-time or per-request knob

The chat template accepts reasoning_effort in low | medium | xhigh, defaults to xhigh, silently aliases high to xhigh, and raises on anything else. MEASURED by reading the template shipped in the GGUF metadata. Only low and xhigh inject an instruction line; medium injects none.

06An image costs one token per 32×32 pixels

Patch size 16 with spatial_merge_size 2 means the vision tower emits one token per 32×32-pixel block before any resize policy. DERIVED from vision_config; measured against a real screenshot in §11.

02The physics

Decode is a bandwidth problem; context is a real-estate problem.

Every token of decode reads the whole weight file out of VRAM. That gives a hard ceiling before any software is involved:

decode t/s  ≈  memory bandwidth  ÷  file size  ×  efficiency

RTX 3090 :  936 GB/s ÷ 14.25 GB = 65.7 t/s theoretical
                                × 0.70 rule of thumb = 46.0 t/s expected
                                MEASURED, no speculation = 42.6 t/s (0.65)

936 GB/s is NVIDIA's own figure for the RTX 3090 CITED (GA102 architecture whitepaper: 384-bit × 19.5 Gbps). Third-party databases quote 936.2, derived from the unrounded memory clock; the difference is 0.02 % and the rounder number is the one with a primary source.

MEASURED 42.61 t/s with --spec-type none, -c 32768, q8_0 KV, temp 0, an 83-token prompt and 700 predicted tokens on an idle desktop. Landing at 0.65 of raw bandwidth is the signature of a correctly, fully offloaded model. Landing at 0.45 is the signature of §10's first failure mode.

The floor is also the most stable number on this page. Repeated across four content types and both token streams — code, prose, copying, reasoning and answering — eight no-speculation measurements at q8_0 KV landed between 41.46 and 42.81 t/s, a 3 % spread. Without a drafter, what you are generating simply is not a variable. (An fp16 cache lifts the same probe to 43.19; the band above is for the q8_0 cache every recipe ships.)

Why the floor matters more than the ceiling

41.5–42.8 t/s is what this model does when speculation cannot help it — eight measurements across four content types and both token streams span 3 %. Every faster number on this page is a speculation result and carries an acceptance rate. If you plan capacity on the fast numbers you will be wrong on the day your workload changes shape.

MEASURED prefill ran 1,082 t/s at 1.5k and 816 t/s at 92.7k — a 25 % decline across a 60× increase in prompt length, peaking at 1,198 t/s in the middle. 05Two ceilings, and only one of them is safe

Fully resident — 163,840 tokens

llama-server takes 22,418 MiB at MTP n4/p0.75, leaving 2,158 of the board. Shallow decode 63.7 t/s, and it stays that way when the window actually fills. The coding drafter's deeper draft adds 898 MiB and cuts that headroom to 1,260.

Shallow-safe — 262,144 tokens

Loads fine. Answers a short prompt at 59.1 t/s. Has 3.5 GiB living in system RAM. Looks like a free extra 98k tokens right up until something reads them.

The difference between those two settings is not visible from a short prompt, which is exactly what makes it dangerous. Same prompts, same flags, same projector — only -c differs. One loose end, left loose. The resident column here reads 30.61 t/s at 90.9k while the projector-less series above reads 35.81 at 92.7k — slower at a shallower depth, on otherwise identical flags. The trap, stated plainly

A reader who set -c 262144 because it loaded and answered quickly would get 26 % of what the resident window gives the first time they pasted a 90k-token document into it — 8.0 t/s against 30.6 for the identical prompt at -c 131072 — and nothing in the logs would say why. That is the entire reason this page reports two ceilings and ships the smaller one.

A short prompt will tell you whether a window fits. It will never tell you whether it is fast.

06Slack is the anti-spill budget

At this model's measured 45,056 B per window token, 1 GiB of headroom is 23,800 tokens DERIVED. That is the unit to think in when someone opens a browser. This desktop's own share of the board measured anywhere from 133 to 1,181 MiB depending on what was open, and a compositor under real load can take several GiB more. Recipe 1 leaves 1,260 MiB for all of that; Recipe 2 leaves 2,668. Dropping one step of -c buys back 1,408 MiB, which is the whole argument for making 131,072 the default.

02q8_0 KV costs 2 % of decode and buys 27 KiB a token

MEASURED at -c 32768: fp16 KV decoded 43.19 t/s using 15,354 MiB; q8_0 KV decoded 42.31 t/s using 14,480 MiB. So the quantised cache is 2.0 % slower and saves 874 MiB at 32k. Do not take the next step down — and this one was not measured here

-ctk q4_0 halves the cache again and is the wrong trade at exactly the long contexts that make you reach for it: the K cache is the half that does not tolerate 4 bits, and the damage compounds with depth, so the setting is worst precisely where it is supposed to help. 04Effort

What the thinking knob actually costs, at n=1.

Qwen3.8 exposes reasoning_effort with three settings and defaults to the most expensive one. Anything that talks to this server and does not set the knob is paying for xhigh, whether or not the task needs it.

# at load time, for the whole server
--chat-template-kwargs "{\"reasoning_effort\":\"medium\"}"

# or per request, in the JSON body
"chat_template_kwargs": {"reasoning_effort": "medium"}
n=1, and one non-blind judge

The methodology this campaign follows asks for two runs per level and independent blind subagent judges. The time budget bought one run per level, scored by a single judge who could see which was which. The cost figures below are real single samples at temperature 1.0 — a non-deterministic setting, so a second run would land somewhere else. The quality column is a first look, not a ranking, and no level is crowned.

02What each level produced

Each answer was checked mechanically against the task's numbered requirements, then rendered headless in Chrome at 1280×720 and looked at. One judge, not blind, n=1 — so what follows is reported as categorical findings (does it work, does it violate a stated requirement), which are meaningful at n=1, and not as a score, which is not.

low — works

20 CONFIG constants, all seven mandated ones present, and every one of the twenty actually referenced in the code. 17 draw functions. No external references of any kind. requestAnimationFrame with delta time and a resize listener. Renders correctly; creatures distributed across the tank.

Missing: no devicePixelRatio handling, so it is soft on a HiDPI display.

There is a small irony in where the cut landed. The 8,557 characters that did arrive end mid-way through a reflow() function that clamps every creature's position into the current canvas bounds — precisely the guard whose absence broke the medium file. The most expensive run was writing the fix the cheaper run needed, and ran out of budget before it could hand it over.

That is not a quality result. It is the memory result from §02 arriving in a different disguise: a level whose thinking appetite exceeds the budget does not produce a worse answer, it produces no answer. The methodology's response to a truncated arm is to raise the cap and re-run that arm alone; the largest cap that still fits inside this recipe's window is 120,000 tokens. That re-run was scheduled as the last GPU job of the campaign on purpose: if it overran the time budget, everything else was already measured and this page could ship the truncation as the finding rather than wait on it. It finished, and the result is the most interesting number in this section.

04The window sets the effort ceiling

A thinking model's effort setting is only available to you if the window can hold what it wants to think. The vendor's own guidance for this model, on a 1M-token deployment, is to allow 262,144 tokens for reasoning content and 131,072 for the final response CITED (model card, “Adequate Output Length”).

That is the whole point of this section. The reasoning budget the vendor recommends is larger than the entire context window this card can hold. The largest fully-resident window measured here is 163,840 tokens — less than two thirds of the recommended reasoning allowance alone. On a 24 GiB card the effort knob is not a quality dial you turn freely; it is bounded by memory, and the binding constraint is the card, not the model.

01How it works here

Qwen3.8 ships a trained multi-token-prediction head. Each round the head drafts up to --spec-draft-n-max tokens, stopping early when its own probability drops below --spec-draft-p-min; the full model then verifies the batch in one pass and keeps the longest correct prefix. One target pass therefore emits one plus the accepted draft tokens, and accepted-tokens-per-target-pass is the quantity that sets your speed — not the acceptance percentage everyone quotes.

Other drafters exist, and none of them were tried. The MTP head is the speculator that ships inside this GGUF, which is the entire reason it is the only one on this page. External drafters — DFlash2 is the current example — are a real alternative, and they were out of scope for a smoke tier: a ~1.14 GB download plus a source build off a PR branch, against a four-hour measurement budget. Nothing here is evidence about them either way. Read their absence as untested, not as a verdict.

04The acceptance demonstration

Same card, same flags, only the content changes. This is the measurement that makes every speculative speed-up falsifiable — and it produced the campaign's most interesting mistake.

It fooled me twice, and both mistakes are more instructive than the number they produced.

First reading — “copying is slower”

At n-max 10 / p-min 0.5, the novel-code probe ran 89.06 t/s (59.2 % acceptance) and the copy-this-verbatim probe ran slower, 59.26 t/s (54.7 %). Copying is supposed to be the trivially predictable case, so this looked like a genuine surprise about the model.

Second reading — “no, it is the draft depth”

At n-max 4 / p-min 0.75 the identical copy prompt accepted 96.3 % and ran 79.64 t/s. That looked like a tidy mechanism: a 10-deep rollout cannot cash in easy content because the MTP head conditions each draft step on its own previous guess, so a 4-deep draft wins. Tidy, and still wrong.

09Sample size

Why this page publishes no accuracy score at all.

The honest answer to “is IQ4_XS as accurate as Q4_K_M?” needs more samples than a four-hour window can buy, and a bad answer is worse than none. Here is the arithmetic that made the call.

For a paired comparison at 95 % confidence and 80 % power, the number of items needed to detect a gap of G accuracy points is roughly:

DERIVED — standard paired-proportion power arithmetic; the ordering is what matters, not the exact counts.
Gap to detectItems neededWhat that gap looks like
20 pts~25A collapse. A broken quant, a wrong chat template.
10 pts~100–150A different model size class.
5 pts~300–500A genuinely worse quantisation.
1–3 ptsthousandsEvery Q4-class quant against every other one.

01A worked example

Suppose you run 25 GSM8K questions and one quant scores 22/25 (88 %) while another scores 20/25 (80 %). The 95 % confidence interval on a single 22/25 is 70–96 % (Wilson, DERIVED). The intervals overlap almost completely. You have measured that neither quant is catastrophically broken, which is worth knowing, and you have measured nothing about which is better. Report it as a smoke test or do not report it.

The right tool for the question

Per-token statistics answer the ranking question that small-n accuracy cannot. One perplexity pass over the wikitext-2-raw test split scores hundreds of thousands of token positions instead of a few hundred all-or-nothing answers — which is why §05 reports perplexity and stays silent on benchmark accuracy.

02The token-budget trap

There is a second way to publish a wrong benchmark number, and it has nothing to do with sample size. A thinking model at xhigh can spend tens of thousands of tokens before it answers. Cap generation too low and the arm truncates: the model was right and you scored it wrong, and the truncations concentrate in exactly the hard questions. The rule is: set the cap where the longest thought cannot reach it, count truncations, and if an arm truncates, raise the cap and re-run that arm. Never filter the test set to the questions that did not truncate — that selects your items on one arm's behaviour and deletes the hard ones.

×

Presenting n=25 as a quant ranking

It detects a 20-point collapse and nothing finer. Label it a smoke test or leave it out.

×

Dropping truncated questions

Selection bias, in the direction that flatters the arm with the biggest appetite.

×

Quoting one t/s number for a model

This page measured 8.0 to 148.7 t/s for the same file on the same card in one evening — an 18× spread, entirely from content, context depth, drafting flags and whether the window was resident. Any single number is a claim about all four that the number does not carry.

12Scope

What a 27B on one consumer card is for.

This page measured speed, memory, energy and image cost. It ran no capability benchmark, so the honest scope statement has to lean on the vendor's own claims and on structure — clearly marked as such.

The one capability observation it does have is §04's: asked for a single self-contained HTML file against a 40-line requirement list, this model produced two complete, dependency-free, ~1,270-line HTML files in one shot — 36,680 and 40,838 bytes, no external references in either — one of which ran correctly and one of which had an initialisation-order bug. That is a real data point about the size class — a 27B at 4 bits will write a lot of correct code in one pass and will also quietly hand you a bug — and it is n=2.

The vendor positions Qwen3.8-27B as a thinking, tool-using, vision-capable model with a 262k native window, and publishes agentic-coding benchmark numbers evaluated at temp 1.0 / top_p 0.95 in a 256k context CITED (model card). Those are the vendor's numbers, on the vendor's harness, at full precision. Nothing on this page confirms or contradicts them, and a 4-bit quantisation on a 24 GiB card is a different artefact from what they measured.

The agentic bucket ran its cost gate and lost. A local DeepSWE-via-Pier pipeline was built and validated end-to-end on this machine on 2026-08-23 — one real sandboxed task, 22 LLM calls against this served model, 9 m 36 s wall — and the single-task run projected ~8.5 hours for the smallest honest sweep (10 deterministic tasks × 3 effort levels, context raised so runs complete rather than truncate). That exceeds the methodology’s ~4-hour gate, so per rule 22: local effort-sweep available but skipped for cost (projected ~8.5 h); published anchor: 42.2 for the base model on the DeepSWE 1.1 leaderboard CITED — full precision, the harness’s own serving stack; a local 4-bit score would read as a ⟨quant, machine, effort⟩ delta against that anchor, and that delta is the unmeasured part. The validation run itself yielded one measured fact worth keeping: the task consumed 1.01 M prompt tokens against 21.7 k completion tokens, so agentic wall time on this class of harness is prompt-processing-bound — prefill speed, not the decode numbers this page spends most of its ink on, is what an agentic buyer should scale by.

What is measurable from here is the shape of the trade. This file is 13.3 GiB. A frontier model is one to two orders of magnitude larger and is not going to run on this card at any quantisation. The interesting question is therefore never “is this as good as the frontier” — it is which tasks are kind-limited and which are degree-limited. A task that needs the model to hold a long file, follow a spec and emit working code is degree-limited: a smaller model does it less reliably, and you find out by running it. A task that needs knowledge the model does not have is kind-limited, and no amount of local speed fixes it.

The number that actually decides it

Writing real deliverables, this card produced 43.8 to 95.4 tokens per second — prose at the bottom, code at the top, both on answer tokens at -c 32768 with the shipped drafter — while drawing a sustained 344 W measured over multi-minute generations, gross, with your data never leaving the machine. That is the proposition. It is not “frontier-equivalent” and this page will not say it is.

13Coding agents

Not measured — and unmeasured means unmeasured.

The methodology asks for an agent-attach matrix: every coding agent tested against the served model with a question only answerable by seeing an attached image, scored PASS / FAIL-honest / FAIL-hallucinated. That phase was cut for time before any agent was launched, so this page publishes no agent configuration, no verdicts, and no “should work” snippets. A config that was never run is a guess, and a guess in a monospace block reads exactly like a measurement.

Two things an integration would build on are established here: the server answers the OpenAI-compatible /v1/chat/completions endpoint with --jinja, and images ride that same endpoint as image_url data URIs (§11). The one flag to get right is reasoning_effort — an agent that does not pass it gets xhigh, which §04 measured at 120 Wh and no deliverable.

The failure to hunt when you do wire one up

Agents drop image attachments silently when a capability flag is missing, and a model that receives no image will often describe one anyway. Test every agent with a question that cannot be answered without the pixels, and treat a confident wrong description as worse than an honest refusal — a standard §11 does not itself meet, and says so.

03What was not measured

Stated plainly so nobody mistakes an omission for a result:

  • Other quantisations. One file was measured. There is no quant ranking on this page and there cannot be one.
  • Benchmark accuracy. No GSM8K, no MMLU, no coding benchmark, at any n. See §09 for why a small one would have been worse than none.
  • The vision critique loop. A screenshot's token cost was measured; whether the model's critique of a rendered page names real content was not.
  • Coding agents. No agent was launched. §13.
  • Blind quality judging. §04's quality note is one judge, not blind, at n=1.
  • Other machines. Every measured row is this RTX 3090. §07's other cards are labelled arithmetic, and the roster rows without a primary link are flagged softer again above.
  • A 4-bit K cache. -ctk q4_0 was never run. §03 carries a caution about it, and a caution is all it is.
  • System RAM under either load mode. --load-mode mmap was verified decode-neutral; its ~15 GB page-cache footprint against --load-mode none was not measured. §03.

Reproducing this

Every configuration in §08 is a complete command line. Run one, send the red-black-tree prompt at temperature 0, top_k 1, and read timings.predicted_per_second out of the response. If your number is far below the one printed here, §10's first two rows explain almost every case.

Blinding

This was run as a reproduction test with the answer key sealed. The machine held a previous campaign's results for this same model; those files, the published report, and every summary and log from that run were never opened.

The one exception is the wikitext corpus in that directory — input data, not a result.

Why 16 and not 64

Gated DeltaNet is a linear-attention layer: it keeps a fixed-size recurrent state instead of a growing key/value history. Three of every four layers here are that kind.

The consequence is not subtle. A conventional 27B transformer with this head geometry would want four times the cache, and 262k would not be a conversation you could have on a 24 GiB card.

The arithmetic is a floor

config.json says 34,816 B/token. The card says 39,936 with the drafter off and 45,056 with it on.

Budget with the number the card gave you. Where the two disagree, the card is not wrong.

Shared memory is the tell

On Windows, nvidia-smi cannot see per-process usage. The GPU Process Memory performance counters can, and their Shared Usage line is where a spill announces itself long before the speed does.

One measurement, twice

The projector's 1,138 MiB was measured two unrelated ways — a mmproj-on/off difference at the native max, and a projector-less versus projector-loaded difference at 32k — and landed on the same figure.

Two cheap metrics agreeing is worth more than one expensive one.

Where the speed numbers come from

llama-server returns a timings object on every completion: prompt_per_second, predicted_per_second, draft_n, draft_n_accepted.

Every t/s and every acceptance figure on this page is read from those fields. Nothing here is a stopwatch divided by a token count.

The mistake worth keeping

The acceptance demonstration was run first at n-max 10 and produced a clean, reproducible number attached to a false conclusion.

It survived here as a case study because how a tidy measurement misleads is worth more than the measurement was.

n=1 means n=1

The effort comparison is a single run per level, judged by one judge who could see the labels. The methodology asks for two runs per level and blind independent judges.

It is published as cost data with a quality note attached, not as a ranking.

Why no benchmark score

Twenty-five questions can detect a broken quant and nothing finer. Running a small benchmark and printing the percentage would have been the most quotable number on this page and the least true one.

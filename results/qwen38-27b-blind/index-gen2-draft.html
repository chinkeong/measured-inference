01What this page is

One model, one card, six rounds of measurement.

This page tells you how to run Qwen3.8-27B on a single NVIDIA RTX 3090 with 24 GiB of memory, using llama.cpp's llama-server. It gives you a command you can copy, the speed that command produced on this machine, the memory it used, the electricity it drew, and the benchmark scores it earned. If you only want to serve the model, go to §03, copy one block, and stop reading. Everything after that exists to justify a choice inside that block, and to tell you what to change when your machine or your work is different from this one.

The four numbers in the strip at the top of the page are the whole speed story in one line, and each carries the condition that produced it. Read them in this order: the floor is what you get when the model's built-in draft head cannot help — that is the number to plan capacity on. The short-context band is ordinary work: writing prose at the bottom of it, writing code at the top. The at-depth band is what you get once about 91,000 tokens are loaded, which is where an agent session lives; it carries three figures because the drafter setting and the token stream both move it — the answer you keep runs at roughly twice the speed of the thinking you throw away. The ceiling is a laboratory number: the model copying text it was given. Nobody works at the ceiling. Every one of the four was measured at temperature 0, which is not what your client will send; the strip says so and §15.03's first entry prices the measurement that would close it.

This page is a blind reproduction test, and the blind ended after the first round. Round 1 was run with the answer key sealed: a previous campaign had measured this same model on this same machine, and its files, its published report and every summary and log from it were never opened while round 1 ran. The single exception was the wikitext corpus, which is input data rather than a result. Everything after 02:19 is post-blind — rounds 2 to 5 were planned in the knowledge of round 1's own findings, and round 6 gates against a published number by design. Every round is labelled, so you can always see which side of that line a number comes from. What even round 1 did not produce for itself is listed in the margin.

02Plain words

Seventeen words, defined once, used plainly after this.

Every technical word this page uses is defined in the box below, with one of this campaign's own numbers attached so the word means something concrete. Nothing later in the page re-defines any of them; later sections point back here instead. Eleven of the seventeen are unavoidable for any local-inference page. Six more — energy per token, draft length, truncation, run, projector and memory bandwidth — are here because this page cannot be read without them: a third of its measurements are about electricity, a third are about a draft head, and every number on the page belongs to one particular server run.

Run
One server started with one exact set of flags, measured, and shut down again. Nothing on this page is an average over settings: every number belongs to a run whose flags are printed beside it. The campaign's round 5 is 17 runs MEASURED that change one thing at a time; two more were written down as skipped. Where a source log calls a run an arm, this page means the same thing.
Token
The unit a language model reads and writes. Roughly three quarters of an English word, so 1,000 tokens is about 750 words. On this page, 700 tokens is the standard probe length, and 17,321 tokens MEASURED is what the model wrote for one complete web page at its cheapest thinking setting.
Context window
The largest number of tokens the server will hold at once — your prompt, the model's thinking and its answer, all together. You set it with -c. This model supports 262,144 tokens CITED; on this card the largest window that fitted entirely in graphics memory measured 163,840 MEASURED — and that ceiling has conditions. It was measured with the conservative drafter (n4/p0.75) and the vision projector loaded. At the n10/p0.5 the coding recipes ship, the same window leaves only 1,260 MiB for the rest of the machine, which is why §03.01 fences it as a bare-desktop configuration and the default recipe is one step smaller.
VRAM
The memory on the graphics card itself. This card has 24,576 MiB CITED. When something does not fit, Windows quietly puts the overflow in ordinary system memory, which is about eighteen times DERIVED slower to read — this card's 936 GB/s against this machine's 51.2 GB/s of DDR4. Everything in §05 is about making sure that never happens.
Memory bandwidth
How fast the card can read its own memory, in gigabytes a second. It is the number that decides writing speed, because the card must read the whole model file once for every token it writes. This card is 936 GB/s CITED; the system memory a spilled window falls back to is 51.2 GB/s. §07 orders other cards on this number and nothing else.
Projector
A second, small file (--mmproj) that turns an image into tokens the model can read. Without it the server rejects pictures; it cannot be added after start-up. It costs 1,138 MiB MEASURED of graphics memory whether you send images or not, and 0 % MEASURED of writing speed (§05.05).
Quantization
Storing the model's numbers with fewer bits so the file is smaller, and therefore faster to read. This page's main file uses about 4.2 bits MEASURED per number and is 13.27 GiB MEASURED on disk. A smaller file is a faster file, because writing each token means reading the whole file once (§04).
KV cache
What the model keeps about every token already in the window, so it does not have to read them again. It grows as the window fills, and it is the reason a bigger window costs memory. On this model one token of window costs 45,056 bytes MEASURED with the draft head on, and 39,936 MEASURED with it off.
Drafter, or draft head
A small predictor that guesses the next few tokens; the full model then checks all the guesses in one pass and keeps the correct ones. The technical name is speculative decoding, and this page uses drafter and draft head for the same thing throughout. Qwen3.8 ships its own drafter inside the file, so nothing extra needs downloading. Turning it on measured 93.9 tokens per second MEASURED writing code against 43.0 with it off, and each token also costs about 40 % of the electricity — 3.21 joules against 8.10 MEASURED (§09).
Acceptance, and mean draft length
Two numbers that describe how the drafter is doing. Acceptance is the share of guesses the full model keeps. Mean draft length is the server's own count of how long each draft round is; it reads larger than the limit you set, so it is counting the batch the full model verifies rather than the guesses alone, and this page quotes it as the server prints it (§15.01). Speed follows the two together, never either alone: the setting with the highest acceptance on this page — 96.5 percent MEASURED — is the slowest one that drafts at all, because its draft rounds are the shortest, 2.86 against 6.28 for the fastest setting MEASURED.
Perplexity
A quality score for a model file, measured by running it over ordinary text and asking how surprised it was by each real next word. Lower is better, and it scores hundreds of thousands of positions instead of a few hundred right-or-wrong answers. This file scored 6.5956 MEASURED with an f16 cache; with the q8_0 cache every recipe actually ships it scored 6.6160 MEASURED (§08.01). It compares two files of the same model family and nothing else — never two different models, because the two would be counting different tokens.
Effort
How long this model thinks before it answers. It has three settings — low, medium and xhigh — and it uses xhigh unless you tell it otherwise. Two numbers, from two different arms, and they must be read together. Score: on a 175-prompt suite, 125 of them scored, the three landed within 1.6 points MEASURED of each other — but only once the token cap was raised and the arms that had been cut off were re-run. Time: the original arms took 1.00, 1.47 and 2.70 hours MEASURED, and the re-runs cost a further 0.38, 0.53 and 2.40 h on top. So the 1.6-point tie is the price of the re-run arms, not of the first ones (§09.02). On that suite, effort buys time, not measurable quality.
Prefill and decode
Two different jobs with two different speeds. Prefill is reading your prompt: about 1,000 tokens per second MEASURED here. Decode is writing the answer, one token at a time: tens of tokens per second. Dividing total tokens by total seconds mixes the two and gives a number that is wrong in a way that gets worse as prompts get longer — 9.2 DERIVED where decode was really 47.1 MEASURED.
Spill
What happens when the window no longer fits in VRAM and part of the cache lands in system memory. Short prompts still look fine; long ones collapse. Measured here: 30.6 tokens per second became 8.0 MEASURED on the identical prompt, purely because the window had been set too large.
Joules per token, and watt-hours
Electricity. A joule is a small unit of energy; a watt-hour is 3,600 of them. This page reports the energy the graphics board itself used, not the energy at the wall socket, which is higher and was never measured here. Writing code with the drafter on costs about 3.2 joules MEASURED a token; one complete web page at the most expensive thinking setting cost 105 watt-hours MEASURED.
Truncation
The model being cut off because it reached your token limit before it finished. It does not give you a worse answer; it gives you no answer, and a benchmark scores that as wrong. On this page, 11 of 12 MEASURED truncated benchmark answers came back completely empty, because the model was still thinking when the limit arrived.
Percentage point versus percent
A percentage point is an absolute unit: 92 % to 96 % is four points. A percent is relative: the same move is 4.3 % better. This page writes “points” for scores and “percent” for ratios, always. Points are chained to questions: in this campaign's benchmark cells, at n=25 one question is worth 4 points — so a four-point difference between two runs is one question going the other way, and the 1.6-point spread the effort sweep found is less than half of one question.

01Why a 27B model fits a 262k window on a 24 GiB card

Most of this model's layers do not keep a growing record of the conversation. Three layers out of every four keep a fixed-size summary instead, rewritten as each new token arrives and never any bigger. Only the remaining quarter keeps the full record. That one design choice is why a window this large is affordable at all, and it is behind most of the surprising numbers further down this page.

02What the drafter actually does

The second idea worth a picture is speculative decoding, because every large speed number on this page comes from it, and every one of them can be checked against two counters the server prints for free. The small draft head guesses a short run of tokens. The full model then checks the whole run in a single pass — one read of the file instead of one read per token — and keeps every guess up to the first mistake. Good guesses buy you several tokens for the price of one. Bad guesses cost you the draft and leave you with the one token you would have had anyway.

03The recipes

Copy one block, serve the model, stop reading.

There are four configurations here because three measured facts split the choice, and each one takes a different decision away from you. One: the vision projector, the extra file that lets you send screenshots, costs 1,138 MiB of graphics memory, and that memory is worth about 26,500 tokens of context — so images and window size trade against each other. Two: the draft settings that are fastest for writing code are not the fastest for writing prose, so what you generate picks the drafter. Three: a bigger window leaves less memory for your desktop, and the three window sizes here are three different answers to how much of the card you are willing to hand over. 01Recipe 1 — code and vision, bare desktop

The largest window on this page that can still receive an image. It fits, and it fits with very little to spare: llama-server takes 23,316 MiB of the 24,576 MiB board MEASURED, leaving 1,260 MiB for the desktop and for slack together, and this desktop wanted between 133 and 1,181 MiB across 26 loads. Run it only when nothing else is drawing on the graphics card — no browser, no video call, no second screen. In plain words: it offers every thinking level, holds two xhigh turns, and writes a 700-token code answer at roughly 79 t/s — the same speed as Recipe 2, because the window size barely moves decode.

Why this recipe is fenced, with the arithmetic printed

1,260 MiB left minus the 1,181 MiB this desktop wanted at its heaviest is a margin of 79 MiB. This exact configuration's own load-to-load spread is 127 MiB: the same command line read 23,316 MiB in one load (data/phase10b.txt) and 23,189 in another (Phase 4d), and this page budgets on the larger of the two MEASURED. The margin is smaller than the noise, so “it fits” is not something this campaign can resolve for a busy desktop — which is the whole reason Recipe 1 is bare-desktop-only and Recipe 2, at 2,668 MiB left, is the default.

05Which effort levels each recipe can hold

A thinking model's effort setting is only available to you if the window can hold what it wants to think. Two different things can take a level away from you, and they have two different fixes. If the window is the binding constraint, a larger -c or a smaller conversation fixes it. If the wall clock is the binding constraint, no amount of memory helps — the level simply costs eighteen minutes and 105 watt-hours for one answer, and you decide whether that is worth it.

06Standardized industry metrics

Here is what each recipe costs in electricity. The board's own power sensor was sampled twice a second and joined to the server's own start and end timestamps for every request, so prefill and decode are separated rather than averaged together. Two versions of every energy figure are printed: gross, which is everything the board drew, and idle-subtracted, which removes what the board draws with the model loaded and answering nothing. The honest marginal cost of running a query sits between them. Joules per token and tokens per kilowatt hour are printed to three significant figures, because this campaign's own replicate spread on the slower arms is 2.9 % — replicate spread means the difference between repeats of one identical run, and three significant figures means three digits that carry information, so 3.21 rather than 3.210. Watt-hours keep more digits, because each one is an integration over a whole run rather than a sampled rate. The precision licence is narrower than it looks: it was §09.05's four whole-deliverable figures (20.58 / 36.01 / 120.25 / 104.84 Wh) that a second tool reproduced to within 0.05 %. The Wh cells in the table below are different numbers, from different runs, and inherit only the argument — that an integration over a whole window is steadier than a sampled rate — not that measured reproduction. The full noise band, and what survives it, is §06.07.

EDP is energy × latency, in joule-seconds — not a power-delay product. 04The facts behind the flags

Eight facts that set every flag you will type.

This section justifies the flags in §03. The one idea to carry away is simple: to write a single token, the card has to read the entire model file out of its memory. That is why a smaller file is a faster file, why memory bandwidth decides your speed more than any other hardware number, and why anything that lets the card produce several tokens per read — the draft head — is worth more than any other flag. Of the other seven, four are about where the memory goes (facts 1, 2, 3 and 7), and three are about what you can ask the model to do: the thinking knob, what an image costs, and the bandwidth law itself.

01Only 16 of the 64 layers pay rent per token

Cache arithmetic counts full-attention layers only: 2 × layers × n_kv_heads × head_dim × bytes. With 16 full-attention layers, 4 KV heads and a 256-wide head, that is 65,536 B per token at fp16 and 32,768 B at q8_0 nominal — 34,816 B once q8_0's per-block fp16 scale is counted. DERIVED from the config.json fetched during this run.

02The other 48 layers are free as the window grows

Each Gated-DeltaNet layer holds a fixed recurrent state (48 × 128 × 128 fp32) plus a 4-tap convolution state — 3.16 MiB per layer, about 151 MiB for all 48, at any context length DERIVED. This is the entire reason a 27B model can hold a 262k window on a 24 GiB consumer card, and it is the diagram in §02.01.

03A window token really costs 44 KiB, not 34

MEASURED: stepping -c from 32,768 to 163,840 moved llama-server's dedicated VRAM in 1,408 MiB steps per 32,768 tokens on three of the four steps — exactly 1,408 each time — which is 45,056 B per token of window with the draft head on. 03Two ceilings, and only one of them is safe

Two windows can both be called a limit, and only one of them is a limit you can use. The first is the largest window whose whole allocation stays on the card. The second is the largest window the server will accept, which is the model's native maximum — it loads, it answers a short question quickly, and it is a trap.

Fully resident — 163,840 tokens

llama-server takes 22,418 MiB at MTP n4/p0.75, leaving 2,158 of the board. Shallow decode 63.7 t/s on a 20-token probe. The coding drafter's deeper draft adds 898 MiB and cuts that headroom to 1,260.

Speed-verified shallow only. No probe on this page ever filled a 163,840-token window. The deepest fill this campaign measured is 90,887 tokens, and it was measured in a 131,072 window — where decode does not stay flat: it falls 86.30 → 64.76 on the cooled answer ladder, reads 70.09 on the shipped recipe, and 35.8–36.6 on the reasoning stream (§06.05). Expect the same shape here. What is established at 163,840 is that it fits and that a short prompt is fast; what it does at depth was not run.

Shallow-safe — 262,144 tokens

Loads fine. Answers a short prompt at 59.1 t/s. Has 3.5 GiB living in system RAM. Looks like a free extra 98k tokens right up until something reads them.

04The collapse, measured

The difference between those two settings is invisible from a short prompt, which is exactly what makes it dangerous. Same prompts, same flags, same projector — only -c differs. The comparison uses 131,072 rather than the 163,840 ceiling because 131,072 is the window the default recipe ships.

The trap, stated plainly

A reader who set -c 262144 because it loaded and answered quickly would get roughly a quarter of what the resident window gives the first time they pasted a 90k-token document in — 8.0 t/s against 30.6 for the identical prompt at -c 131072 — and nothing in the logs would say why. That is the entire reason this page reports two ceilings and ships the smaller one.

A short prompt will tell you whether a window fits. It will never tell you whether it is fast.

05What the projector costs, and what it does not

For most of round 1 it looked as if loading the vision projector cost about 15 % of decode at depth: one probe read 30.61 t/s with it loaded where another read 35.81 without, at a shallower depth. Round 2 ran exactly the probe that question deserved — byte-identical prompts filling 90,862 tokens, loads in ABBA order, the probe fired straight after prefill recorded and then discarded, 45 s of cooling before each measured one, five probes per load. With the drafter off, projector-loaded pooled 26.965 t/s against 26.975 without — 0.04 % apart, against a within-arm spread of 0.4 %. Repeated with the drafter on: 62.71 against 62.655, 0.09 % apart, with draft acceptance matching probe for probe.

Why those four figures are printed to five digits when the rest of this page uses three. They are pooled medians over five cooled probes per arm, not single levels, and the result being reported is a null of 0.04 % — which cannot be stated at all in three significant figures. §06.07's three-figure rule is for single-probe levels; a cooled, pooled null is its named exception, along with perplexity.

The projector's entire cost is the memory. 19,376 − 18,238 MiB in the first pair and 21,034 − 19,896 in the second — 1,138 MiB twice more, and 0 % of decode MEASURED. What produced the 30.61 was the measurement, not the configuration; §06.07 is about that, because it puts a band on every single-probe level on this page. The 30.61 is quoted in three other places — the §02 glossary's spill entry, the “trap, stated plainly” callout in §05.04 and §06.07's list of what survives the noise band — and in all three it is the resident half of the spill comparison, where the level does not have to be exact for the 3.82× ratio to survive. It is only as an attribution to the projector that it was wrong.

06Slack is the anti-spill budget

At this model's measured 45,056 B per window token, 1 GiB of headroom is 23,800 tokens DERIVED. That is the unit to think in when somebody opens a browser. This desktop's own share of the board measured anywhere from 133 to 1,181 MiB across 26 loads — 26 loads in total, of which the 17 fully resident ones feed the budget model above — depending on nothing but what was on screen. A compositor under real load can take several GiB more. Recipe 1 leaves 1,260 MiB for all of that; Recipe 2 leaves 2,668. Dropping one step of -c buys back 1,408 MiB, which is the whole argument for making 131,072 the default.

Shared memory is the tell

On Windows, nvidia-smi cannot see per-process usage. The GPU Process Memory performance counters can, and their Shared Usage line is where a spill announces itself long before the speed does.

Read it as a step, not a threshold. A steady 116–426 MiB of shared mapping is the normal Windows display model and not a spill: no power-matrix arm spilled, and 16 of the 17 instrumented arms report a non-zero shared figure — the no-server idle arm reads 0. The two power-cap arms are recorded as skipped and produced no reading at all.

06Speed

How fast, what slows it down, and how much of that you can believe.

Four things set your speed, in this order of size. Turning on the built-in draft head is worth roughly double on code — and only 1.16× on prose, which is the same measurement seen from the other end. It needs no download, but it is not free in memory: it costs 1,008 MiB plus 5,120 B a window token, which is 1,648 MiB at the default recipe's window, and §06.04 argues that on a pure writing workload that is hard to justify. Getting -ngl 99 right is worth 30 % and is the single easiest thing to get silently wrong. What you are generating is worth up to 3.4×, because predictable text drafts well and free-form reasoning does not. And how much context is already loaded is worth about a quarter of your speed over a 90,000-token window.

Two further things on this page move speed by more than a few percent, and both are named rather than folded in. Running two requests at once measured +60.3 % of aggregate throughput with the drafter off (§06.06) — it is quarantined, not shipped, because a prior campaign measured the opposite with the drafter on. And letting the window spill into system memory costs 3.82× (§05.04) — that is a failure, not a setting. Apart from those two, nothing else here moves speed by more than a few percent.

And here is why acceptance rate alone still misleads

Look at the copying row. n4/p0.75 accepts 100.0 % — a perfect score, 424 of 424 draft tokens — and runs 97.0 t/s. n10/p0.5 accepts less, 99.0 %, and runs 148.7. The reason is the quantity that actually matters: accepted tokens per verify pass, which is 3.96 for the 4-deep draft and 10.54 for the 10-deep one DERIVED. A perfect acceptance rate on a short draft is a rate limit, not an achievement.

Two quantities, two names, and both formulas printed, because this page carries both. Every verify pass emits one token of the target model's own plus whatever draft tokens it accepts, so the number of verify passes in a generation is predicted_n − draft_n_accepted. From that:

  • Accepted tokens per verify pass = draft_n_accepted ÷ (predicted_n − draft_n_accepted). This is the quantity above. Copy probe, n4/p0.75: 424 ÷ (531 − 424) = 3.96. n10/p0.5: 485 ÷ (531 − 485) = 10.54. It counts what the drafter contributed.
  • Predicted tokens per verify pass = predicted_n ÷ (predicted_n − draft_n_accepted). This is the quantity §09.01's table column reports. It counts every token the pass delivers, so it is always exactly one more than the accepted figure: 4.96 and 11.54 for the same two probes.

They differ by a constant 1, which is small at n10 and large at n2, and that is precisely why the two must not be swapped: a ratio taken on one does not equal the same ratio taken on the other. §09.01's prose depends on which one is used, and says so there.

05Depth, and what actually changes at 91k

Decode declines as context fills, because each new token has to read more cache. Over a 90,000-token window that costs about a quarter of your speed — a real cost, and a predictable one. What costs far more than depth is whether the model is thinking: at the same 91,000-token prompt on the same server, the answer stream ran 62.0 t/s and the reasoning stream ran 36.6. If a client sets no reasoning_effort it gets the model's default, xhigh — not the medium the recipes ship — and over a long document that is the lower number. No at-depth measurement exists for medium; expect it between the two.

The mechanism is draft length, not acceptance

The controlled pair at 91k is the cleanest result in this section. Acceptance is 0.895 with thinking on and 0.907 with it off — essentially identical, and it says nothing about the 1.69× gap. Mean draft length is 2.99 against 4.31. With --spec-draft-p-min 0.75, the confidence gate truncates the draft tree on the less predictable reasoning stream; acceptance stays high because the gate is discarding the uncertain part. Acceptance rate is blind to the loss; mean draft length is the counter that predicts throughput. That also explains §06.03's result that the highest-acceptance setting is the slowest.

A wider tree recovers only part of it. At the same depth with thinking on, n10/p0.5 reads 38.67 t/s against the shipped n4/p0.75's 36.62 — +5.6 %, against the +12 % the same change wins on shallow code. The no-drafter floor at that depth is 27.01 with thinking on and 26.95 with it off: identical, confirming once more that all content dependence is a speculation effect.

07How much of any of this you can believe

Read this before quoting any single number from this page. Two instruments produce almost everything here, and each has its own repeatability, measured by running one fixed configuration several times and looking at the spread.

The noise floor, stated once for the whole page

Speed, from a single probe fired immediately after a long prefill: about ±25 %. Four runs of one identical configuration read 18.27, 18.82, 19.21 and 26.60 t/s MEASURED. Those four span 45 % from bottom to top; expressed as a band around their midpoint of 22.4 t/s that is ±19 %, and against the best of them it is −31 %. This page rounds it to ±25 % and uses that one figure everywhere — that is the arithmetic joining the “45 % swing” to the “±25 % band”, and there is no second speed noise floor on this page. The cause is the boost clock, not heat: inside one cooled load, five probes ran from 57 °C to 82 °C and decode moved 1.0 %. The fix costs a minute a point and is what round 2 used: discard the post-prefill probe, cool for 45 s, take several probes off the cached prefix, report the median.

Speed, from a cooled repeat probe on a warm server: 0.4 % to 3 %. Within-arm spread across five cooled probes measured 0.4 %; the two probes per server in round 2's drafting sweep spanned at most 3.03 % — that widest pair is Q4_K_M at n10/p0.5, 80.49 against 82.93 MEASURED. The widest IQ4_XS pair is 2.92 % (92.51 against 95.21), which is the figure §15.05's pass band is anchored on, because that check runs on IQ4_XS.

Energy: 2.9 % on J/token, 5.6 % on EDP — and it is configuration-dependent. Measured by running three arms in triplicate. The slow drafter-off arms carry the 2.9 %; the fast MTP arms agree to 0.03 %. Separately, a J/token difference of up to ±6 % between two arms measured hours apart is instrumental drift, not the variable under test — §09.08 has the mechanism, which is the board's own SM clock drifting 11.7 % at constant throughput.

What survives. Ratios and shapes survive both bands: the drafter's 2.18×, the 3.4× content spread, the 3.82× spill penalty, the 2.52× energy win — which §09.06 shows is that round's 2.50× throughput gain rather than something on top of it — and the 14× depth cost. So do categorical findings: it fits or it does not, it truncated or it did not. Levels do not, unless they were cooled and repeated. That is why the header strip quotes 65 t/s at depth rather than 64.76, and why the energy tables print three significant figures.

Where four figures do sit on a single probe, and how to read them. This page prints the server's own predicted_per_second as the server returned it, which is four figures, even where the cell is one probe. Four tables do that: §05.01's shallow-decode column (20-token probes), §03.06's menu decode column, §06.05's reasoning ladder (single post-prefill probes, so ±25 %), and §06.04's answer-token table. Read every one of those as a three-figure level. The digits are printed rather than rounded away so that a reader can find the same value in the raw logs; they are not a precision claim, and no argument on this page turns on a fourth digit that came from a single probe. The two named exceptions where extra digits are load-bearing are perplexity, which reproduced to four decimals, and §05.05's pooled cooled nulls, where a 0.04 % difference cannot be stated in three.

A note on printed precision, since it follows from the band above. The energy tables print three significant figures for joules per token and tokens per kilowatt hour, because the replicate spread on the slow arms is 2.9 %; watt-hour columns keep more, because they are integrations of a whole run and were independently reproduced to 0.05 %. The two fast MTP arms replicate to 0.03 % and their fourth digit is real — 3.210 and 3.743 — but it is not printed, because nothing on this page turns on it. Perplexity is the exception and keeps four decimals, because the same file was re-run twelve hours later and reproduced to four decimal places (§08.03).

An instrument failure, quarantined — not a model result

The cross-family arm's first attempt returned a perplexity of 1,159.72 WITHDRAWN for a well-regarded 12B model file. That reading is withdrawn from every table on this page and must never be quoted as a property of that model; it appears here once, in prose, only because it is the subject of a self-correction. It is an apparatus reading, and the evidence is decisive: the same file, same build, under llama-server -ngl 99 -c 8192 -fa on --jinja, wrote 1,147 tokens of correct JavaScript at 82.1 t/s and passed every repetition and format detector. A model at perplexity 1,159 cannot do that.

An 11-arm isolation ruled out the obvious causes: it is not flash attention (off gives 2,168 against 2,196 on the first chunk), not the sliding -window cache, not memory mapping (with and against are bit-identical, which also proves the runs are deterministic), not the CUDA backend (CPU-only is worse), and not that particular quantisation (a near-lossless file of a sibling model breaks the same way). The signature is that first-chunk perplexity rises monotonically with context — 127 at -c 1024, 956 at 2,048, 1,683 at 4,096, 2,196 at 8,192. More context makes it worse, which no healthy model does. The control in the same harness is clean: this page's own file returns its exact published first-chunk value.

What is established is that the perplexity path is broken for that model family on this build; why is not established. It is recorded as an open instrument defect (§15.03, entry 12), not diagnosed, and the cross-family comparison is carried entirely by the scored benchmark arm — which is what the methodology designates for cross-family work anyway, because perplexity is tokeniser-bound.

09Effort and energy

What the thinking knob buys, and what a token costs in joules.

This model thinks before it answers, and it thinks as hard as it can unless you tell it otherwise. Set reasoning_effort explicitly: no other line in the configuration changes as much. Two individual prompts make it concrete. MATH-500 prompt 3 at xhigh needed 18,273 tokens and was correct; HumanEval prompt 24 needed 17,025 and was correct. Both scored zero at the 16,384 cap. And not every case is a long solve: three xhigh prompts run past 32,768 as well — HumanEval 5, HumanEval 21 and MBPP 8 — and those are genuine non-terminating loops inside the reasoning block, reported as such rather than filtered out.

What licenses re-running only the arms that truncated

Re-running three whole arms would have cost hours to reproduce identical numbers, so only the datasets that actually truncated were re-run. The justification is that greedy decoding is deterministic, and this campaign measured it rather than assuming it: every prompt that did not hit the old cap was compared byte for byte between the two runs. low 24/24, medium 48/48, xhigh 67/67 — 139 of 139, zero drift MEASURED, with -c doubled as well as the token cap. Raising the budget changed nothing about any generation that had room to finish.

04What each level produced, at n=1

The benchmark sweep says the three levels are indistinguishable on short questions. A separate, much smaller test asked each level for one long deliverable. Its results are categorical — does the thing work, does it violate a stated requirement — which is meaningful at n=1 in a way a point score is not.

low — works

20 configuration constants, all seven mandated ones present, and every one of the twenty actually referenced in the code. 17 draw functions. No external references. Renders correctly; creatures distributed across the tank. Missing: no high-DPI handling.

medium — better code, real bug

21 draw functions including unprompted extras, high-DPI handled, and scenery in normalised coordinates so it survives a resize — architecturally the better file. The browser reports nothing.

At n=1 and temperature 1.0 this is not evidence that medium is worse than low, and no level is crowned anywhere on this page. It is evidence that this model, at this size, on this task, will ship an initialisation-order bug that a browser does not complain about — and that reading the output matters more than the effort setting you chose. Every generative probe in this campaign is a greenfield task: write this file from scratch. The one read-then-edit task anywhere in the campaign is the sandboxed repair run in §14, and it failed its tests at n=1. Why effort changes J/token here and does not change it elsewhere

The table above shows J per decode token rising 4.26 → 6.60 with effort. A separate measurement across 115 requests of the benchmark sweep shows effort making no difference at all: the same benchmark at two effort levels reads 7.92 against 7.95 J per token, 0.3 % apart, while the answers differ 3.1× in length.

Both are correct and the difference is the drafter. On this board J per token is decode-phase mean watts divided by decode tokens per second, with no residual — the arithmetic predicts 4.24 / 5.16 / 6.60 / 6.13 against the measured 4.26 / 5.18 / 6.60 / 6.13. It closes here on the whole-window means only because these are 4–21 minute runs whose prefill is 1.6–1.9 s; on the short arms of §03.06 it does not, which is §09.06's dated correction. With the drafter on, effort changes decode speed (because it changes how predictable the stream is), so it changes J per token. With the drafter off, decode is pinned at 38–40 t/s whatever the effort, so J per token does not move. Effort always changes joules per answer; it changes joules per token only when a drafter is running.

Why that 38–40 sits below §06.02's 41.4–43.0 floor band, since both are drafter-off IQ4_XS. They are not the same measurement. The floor band is fourteen shallow probes at -c 32768 on a board that has just started. The 38–40 is the server's own token-weighted rate over hours of continuous generation at -c 65536 with a cache that fills as each answer runs, on a board whose clock has drifted down 11.7 % (§09.08). Both are real; plan a long session on 38–40 and a short one on 41–43, and do not average them.

Confident invention. The travel-writing prompts drew fluent, well-organised answers containing things that are not true — a “Hawaiian $2 bill”, a claim that the first surfers ever to ride a wave did so at Sunset Beach, a misdated battle, a hula centre that does not exist, mistranslated Hawaiian words. One xhigh ALPACA answer expanded into 100 near-duplicate list entries that collapsed into nonsense. Another repeated the same two words three times each to pad a list to the requested length. This is a gap in this page's own instruments, not a footnote: the repetition detectors used elsewhere in this campaign look for immediate and line-level repeats, and none of these three shapes trips them.

One failure that belongs to the model, not the dial. On an ALPACA prompt demanding a full sentence, low and medium independently returned the same bare noun phrase, and every seat rated both a 3. When two settings fail a prompt identically, the effort dial is not the variable under test.

What kind of instrument this is — the limit, stated with the result

The answers were written by Qwen and read by Claude, so nothing here grades its own work; that is the rule this page was waiting on and it is satisfied. It is not independence in the strong sense: the judge and this report's author are both Claude models, a correlated instrument. The mitigations are real and partial — three seats rather than one, blinding by sealed key, a separate shuffle seed per seat, seat spread published beside every mean, and arm-against-arm conclusions drawn from the paired test rather than the raw means. A known residual bias is that judges reward length; these seats were instructed against it and reported correcting for it, which is self-report, not proof. Still open: a judge from another vendor, or human raters. The blinded packets, the sealed key and all 450 ratings are kept, so any other judge can be run over exactly these answers and compared.

One condition that is not eliminated. A seat sees several answers to the same question inside one shuffled batch. This is not a clean-room single-answer protocol, and the condition travels with the numbers rather than being asserted away.

10Sample size

How many questions is enough, and what 25 can honestly say.

A benchmark cell of 25 questions can tell you that a model file is not broken. It cannot tell you that one file is better than another, because at 25 questions the uncertainty on a single score is about ±11 to ±18 points and the real gap between two healthy 4-bit files is one to three. That is why this page ranks quantisation files on speed and energy, where the measurement is precise, and refuses to rank them on accuracy, where it is not. 04The token-budget trap, which overturned a headline here

There is a second way to publish a wrong benchmark number and it has nothing to do with sample size. A thinking model can spend tens of thousands of tokens before it answers. Cap generation too low and the arm truncates: the model was right and you scored it wrong, and the truncations concentrate in exactly the hard questions and in exactly the arm that thinks hardest. This campaign did not merely warn about that. It walked into it.

The rule is: set the cap where the longest thought cannot reach it, count truncations, and if an arm truncates, raise the cap and re-run that arm. Never filter the test set to the questions that did not truncate — that selects your items on one arm's behaviour and deletes exactly the hard ones. This campaign's own hardest case needed 18,273 tokens and was correct; at the original cap it scored zero.

And the re-run does not have to be a whole arm. Greedy decoding is deterministic, so any generation that had room to finish under the old cap produces byte-identical output under a larger one — which this campaign measured rather than assumed: 139 of 139 non-truncated prompts reproduced byte for byte across the cap raise, with the window doubled as well. That turns a licensing argument into evidence, and it is the cheapest credibility upgrade available to anyone re-running a scoped arm.

01Client-contract failures, which are a different class

These five have nothing wrong with the server. Every one of them is fixed in a different file from the server command, which is why they are stated together and up front rather than scattered.

  • One shared token pool. --parallel N divides the window: two slots at -c 131072 give each request 65,536 tokens, not 131,072. llama-server prints the real figure as n_ctx_slot at startup — read it rather than assuming.
  • Client-side cut-offs. A max_tokens that is too small returns finish_reason="length" and an empty content, which reads exactly like a model failure. The measured sizes to use per effort level are in §03.05.
  • No seamless resume. A cut generation cannot be continued; you re-run it and pay for it twice. At xhigh that is up to 21 minutes and 120 watt-hours for nothing, measured.
  • Timeouts. One xhigh answer took 21 minutes 18 seconds. Default HTTP client timeouts are typically a small number of minutes, and the request will be abandoned client-side while the server is still working perfectly.
  • Conversation overflow. A coding agent driving this server at -c 65536 overflowed the window after 22 calls on one real task MEASURED. What the server does at the turn that overflows — error, context shift, or a full re-prefill — and what that costs in wall clock, is entry 4 in §15.03.

What a screenshot costs, and the control this page did not run.

13Scope

What a 27B on one consumer card is actually for.

This is a 13.3 GiB file running on a card you can buy second-hand. It writes complete, dependency-free code in one pass — though not always working code: of the three long files this campaign asked it for, one ran correctly, one shipped a silent initialisation-order bug a browser reports as nothing, and one was the strongest of the three (§09.04). On the one read-then-edit repair task anyone here ran, it fixed nothing: 0 of 96 target tests (§14), at n=1. It reads 90,000-token documents, it sees screenshots, and it does all of that on your own machine at roughly 43.8 to 95.4 tokens a second while drawing about a third of a kilowatt. What it is not is a frontier model, and this page will not say it is. The useful question is never “is this as good as the frontier”; it is which tasks are limited by kind and which by degree.

01What this campaign measured about capability

Five scored benchmark sets ran at 25 questions each across three effort levels — 375 scored generations out of the 525 the suite produced — greedy, with the draft head off so the scores are clean. Pooled over the four all-or-nothing sets, each arm answered 95 to 97 of 100 items correctly (§10.03), and the three effort levels were statistically indistinguishable. Read that as a health result rather than a capability claim: GSM8K saturated at 100 % on every arm, which means the suite has no room left to discriminate at the top, and 25 questions per cell was never going to rank anything finer than a collapse. The suite hash is published in §09.02 so another run can be compared with this one; two runs compare only if their hashes match.

On generative work the observation is smaller and more concrete: asked for a single self-contained HTML file against a 40-line requirement list, this model produced three complete, dependency-free files with no external references in any of them — the one whose length this campaign recorded runs to 1,180 lines — one of which ran correctly, one of which shipped an initialisation-order bug a browser reports as nothing, and one of which was the strongest of the three. That is a real data point about the size class, and it is n=3.

The vendor positions Qwen3.8-27B as a thinking, tool-using, vision-capable model with a 262k native window, and publishes agentic-coding benchmark numbers evaluated at temperature 1.0 in a 256k context CITED (model card). Those are the vendor's numbers, on the vendor's harness, at full precision. Nothing here confirms or contradicts them, and a 4-bit quantisation on a 24 GiB card is a different artefact from what they measured. The vendor lean is now needed only on the agentic axis, which is §14 — the scored axis has measurements of its own.

02Kind-limited against degree-limited

A frontier model is one to two orders of magnitude larger and is not going to run on this card at any quantisation. So the shape of the trade is what is measurable from here. A task that needs the model to hold a long file, follow a specification and emit working code is degree-limited: a smaller model does it less reliably, and you find out by running it — this campaign found out three times, and got a working file twice. A task that needs knowledge the model does not have is kind-limited, and no amount of local speed fixes it.

The proposition, with its conditions

Writing real deliverables, this card produced 43.8 to 95.4 tokens per second — prose at the bottom, code at the top, both on answer tokens at -c 32768 with the shipped drafter — while drawing a sustained 306–341 W with the drafter off and 339–345 W with it on, measured as a range because the board's own clock drifts at constant throughput (§09.08), gross, with your data never leaving the machine. At depth the honest figure is lower and it is the one to plan an agent session with: 37–39 t/s over a 91,000-token document at the model's default xhigh — which is what a client that sets no reasoning_effort gets. The recipes here all ship medium, and no at-depth figure was measured for it; the shipped recipe's own at-depth answer-token figure is 70.1 t/s. That is the proposition. It is not “frontier-equivalent” and this page will not say it is.

02The configuration that worked, with its four traps

This is a configuration that ran, not one that ought to work, which is the only kind this page prints.

  • Declare the model class explicitly. The runner needed --ak model_class=null; without it the harness guessed a class that did not match this server's responses.
  • Serve on port 80. The sandbox's proxy only allows a short list of ports outbound, and the conventional 1234 is not on it. The server was moved rather than the proxy reconfigured.
  • Address the Windows host from inside WSL2 by its virtual address — here 192.168.128.1, not localhost.
  • Give it at least -c 131072. At -c 65536 the conversation overflowed the window after 22 calls on this one task MEASURED. That is the same arithmetic as §03.05: with thinking preserved, every turn stays in the window.

Two further things an integration builds on are established elsewhere on this page: the server answers the OpenAI-compatible /v1/chat/completions endpoint with --jinja, and images ride that same endpoint as image_url data URIs (§12.04). The one flag to get right is reasoning_effort: an agent that does not pass it gets xhigh, which §09 measured at 105–120 Wh and, once, no deliverable at all.

03The attach matrix — not measured, and unmeasured means unmeasured

The protocol asks for every coding agent to be tested against the served model with a question only answerable by seeing an attached image, scored PASS / FAIL-honest / FAIL-hallucinated. That phase was cut before any agent was attached, so this page publishes no attach verdicts and no per-agent configuration snippets. A configuration that was never run is a guess, and a guess in a monospace block reads exactly like a measurement. The gap is entry 19 in §15.03, with the measurement that closes it and its price.

The failure to hunt when you do wire one up

Agents drop image attachments silently when a capability flag is missing, and a model that receives no image will often describe one anyway. Test every agent with a question that cannot be answered without the pixels, and treat a confident wrong description as worse than an honest refusal — a standard §12.02 does not itself meet, and says so.

03The register — what was not measured

Stated plainly and in one place, so nobody mistakes an omission for a result. This is the only place on the page where a standing “not measured” claim lives; every chapter points here instead of asserting its own negation, because a list in one place is a list somebody maintains. Prices are estimates derived from this campaign's own phase ledger, and they are labelled as such — they are not measurements. Closed items stay in the list, marked closed.

1. The sampling-regime bridge

Every speed number on this page was taken at temperature 0 / top_k 1, while the recipes leave sampling to the client and the model card recommends temperature 1.0 / top_p 0.95 / top_k 20 for thinking. Acceptance is a property of which token the drafter must guess, so sampling moves it directly. Every speculative band on this page is therefore greedy-only and non-transferable. Closed by: the drafting sweep plus one depth point re-run at the shipped sampling, n ≥ 3 per arm because temperature 1.0 is not deterministic, reported against the greedy band as a transfer factor.

Price: ~30 min GPU (estimate)

2. Retrieval quality at depth

This page ships windows of 131,072 to 180,224 tokens verified only for speed and residency. No retrieval or needle probe was run at any depth. The KV-quantisation argument is worse than that: q8_0 and q4_0 were verified with a perplexity pass at -c 8192, which structurally cannot see a retrieval failure at 180k. Every shipped window beyond 8k is speed-verified and quality-unverified at depth. Closed by: a needle-in-haystack grid at 8k / 90k / 180k × {f16, q8_0} KV, n=5 per cell, scored on exact retrieval.

Price: ~1–2 h GPU (estimate — prefill-bound; the 180k cells dominate)

3. The prefill-scaled roster

§07 derives every non-measured card from bandwidth ÷ file size — the decode law — and is then read as buying advice for agentic work, which §14 measured to be prompt-bound at about 47 : 1. A decode-ordered roster is the wrong ordering for that workload. Closed by: a prefill-scaled row beside each decode row, anchored on this machine's measured prefill throughput and scaled on each card's published compute rather than its bandwidth, with every borrowed specification graded. Related and partly open: four of the roster's bandwidth and capacity rows were not re-verified against live vendor pages during this campaign — the DGX Spark and the three Intel Arc parts, which are carried from a prior campaign's fact-check dated 2026-08-22. Every other row was checked, at 00:37 on 2026-08-23, and that check produced two corrections this page carries (the 3090 at 936 rather than 936.2, and the 4060 Ti at 288 rather than 554). The grading in §15.02 records which row is which; re-checking the remaining four is the same kind of afternoon.

Price: zero GPU time — one afternoon of arithmetic and specification checking

4. The overflow event

§03.05 publishes a turns-per-window budget and §14 records that a real agent overflowed a 65,536-token window after 22 calls. What the server actually does at the turn that overflows — error, context shift, or a full re-prefill — and what that costs in wall clock, was never observed. Both parents of this page recommend the model for multi-turn coding agents without measuring it. Closed by: one server with --reasoning-preserve on at a deliberately small -c, driven past the window, recording the turn N+1 behaviour and its wall clock.

Price: ~20–30 min GPU (estimate — one server, no restarts)

5. What --load-mode costs in system RAM

The recipes ship --load-mode mmap, justified on load time and decode neutrality — both measured. The system-RAM footprint, roughly 15 GB of page cache held by the mapped weight file, which is the entire reason the alternative flag exists, was never examined. A reader with 16 GB of system RAM should treat this flag as untested for their case rather than recommended. Closed by: one \Process(llama-server)\Working Set and system-wide available-MB reading per mode, per load.

Price: no GPU time, ~10 minutes wall

6. Image-token budget quality, and the withheld-image control

--image-max-tokens 1024 cuts a 1440p screenshot 3.6×; what that costs in what the model can see was not measured, so the recipes omit the flag rather than recommend it. Separately, §12.02's perception observation lacks a withheld-image control, so it is a transport check and not a perception result — and the full critique loop (render the model's code, screenshot it, send it back, judge whether the critique names real defects) was never attempted. Closed by: the same image at two budgets, asked a question whose answer depends on fine detail, scored blind; plus one control run with the image withheld.

Price: ~15 min GPU (estimate — the vision runs took about a minute each)

11. Two of the seven benchmark sets carried no score — closed 2026-08-24

ALPACA and MT-Bench are judge-gated, and for most of this campaign no judge endpoint existed, so every composite index was over five sets and said so. That gap is now closed. On 2026-08-24 a blind panel of three Claude Opus 5 seats read all 150 kept answers and returned 450 ratings with none missing: opaque salted identifiers, the identifier-to-arm map sealed in a key no seat opened, a separate shuffle seed per seat, the standard 1–10 single-answer rubric, normalised (r−1)÷9×100. Both indices are published — the five-set one because every earlier comparison on this page is against it, the seven-set one because that is what the protocol specifies.

What it bought. The judged pair is the only instrument in this campaign that separates the effort levels at all. On a paired bootstrap over the same 25 prompts, medium beats xhigh on MT-Bench by 0.51 rating points (95% interval −0.80 to −0.21), winning 14 prompts to 3 with 8 tied. Every other pairing is a tie, and medium's 0.44-point ALPACA lead over low clears zero by 0.013 and is reported as marginal, not as a result.

What did not close. The answers are Qwen's and the judge is Claude, so the rule that a model must not grade its own outputs is satisfied — but the judge and this report's author are both Claude models, which is a correlated instrument rather than an independent one. Three seats, a published seat spread of 0.28–0.92 rating points, and paired tests are mitigations, not a fix. Still open: a judge from a different vendor, or human raters. The blinded packets, the sealed key and all 450 ratings are kept, so any other judge can be run over exactly the same answers and compared.

Price paid: zero GPU. Price of what remains open: one judging pass by a non-Claude model, or a human panel — the packets are already built and blinded

04The fourteen self-corrections

Counted from the log, in the order they happened. Each one is kept in place with the wrong version still shown.

  1. What the speed probes were timing. Every probe in rounds 1's early phases was timing reasoning tokens, not deliverables, because a 700-token cap never reaches the answer at the default effort. §06.04.
  2. Which drafting flags win. A single-prompt sweep chose a winner that lost on two of four content types. §06.04.
  3. How much VRAM the shipped recipes need. The deeper draft costs 898 MiB, which the ceiling sweep had not included; two of four recipes were changed before publication. §05.02.
  4. Where the effort ceiling sits. It is a distribution, not a number: two samples landed on opposite sides of the same cap. §09.04.
  5. The 81.7 t/s “phantom”. Acquitted — it reproduces exactly and was a mislabelled token regime, not a bad measurement. It is Q4_K_M at n10/p0.5 on answer tokens with thinking off, and it had been filed beside reasoning-token figures. It now appears with that label in §03.06's menu (row 8), §06.03, §08.02, §08.05 and §15.05. No figure changed; only its condition string did, which is why it carries no SUPERSEDED marker.
  6. The 30.61 t/s outlier. Reattributed from “the projector costs 15 % at depth” to a post-prefill clock ramp. §05.05.
  7. The speculation mechanism itself. Mean draft length, not acceptance rate, predicts speculative throughput — identical acceptance, 1.69× the speed. §06.05.
  8. An energy join that fabricated a win. A full token count charged against a partial power window reported 5.32 J per token, which is physically impossible. §11.
  9. The idle baseline. 33.2 / 34.6 W no-server against 30.7–31.1 W loaded SUPERSEDED was physically backwards — an idle board cannot draw more with no model on it than with one resident — and is now 29.9 W no server against 34.1 W loaded. §03.06.
  10. “344 W sustained.” SUPERSEDED Replaced by two bands — 306–341 W drafter-off, 339–345 W drafter-on — because the board's own clock drifts 11.7 % at constant throughput. §09.08.
  11. Three scoring bugs, worth 32, 8 and 4 points. Found by reading an extraction audit, fixed symmetrically, all arms re-graded offline. §09.03.
  12. “Quality falls with effort.” Reversed by raising the token cap: the entire penalty was the cap. §10.04.
  13. A perplexity result withdrawn as an instrument failure. An 11-arm isolation established that the measurement, not the model, was broken. §08.04.
  14. “Board watts fall when the drafter is on.” This page read 325 → 308 → 302 W across the three speculation arms SUPERSEDED and concluded that the energy win compounded on top of the throughput win. Those are whole-window means: each folds in a short, low-power prefill segment, and prefill is a larger share of a shorter run, so the fastest arm looked coolest for a reason that has nothing to do with power. Split by phase, decode watts are 344.6 → 341.7 → 341.0 W, flat to 1.0 %. The 2.52× energy saving is the 2.50× throughput gain and nothing more. Found by noticing that J/token = W ÷ t/s did not close against the whole-window means. §09.06, §03.06.

Run this and you will know within a few minutes whether your machine matches this page. It is one command, one request, and one number with a pass band derived from this campaign's own repeat spread.

# 3. Read timings.predicted_per_second from the response body.
Expected: 93.9 t/s · PASS BAND 91–97 t/s

The pass band is ±3 %, and it is anchored rather than guessed: the two probes of this exact configuration on this machine read 92.51 and 95.21 t/s, a 2.9 % full-width span, which is ±1.4 % about their mean. The band is deliberately set at roughly double that, to cover a different build, a different driver and a different desktop. Anything inside 91–97 reproduces this page.

Outside the band, in order of likelihood. Around 43 t/s: the draft head is not running — check the server log for unused tensor blk.64, which means --spec-type did not take. Around 82–84 t/s: two different causes land in the same place, so read the server log — Q4_K_M at these flags measures 81.7, and this file at the more conservative n-max 4 / p-min 0.75 measures 83.5. Around 30 t/s or below: §11's first two rows explain almost every remaining case — the -ngl off-by-one, or a window too large for the board. Anywhere between, but not repeatably: you are firing a single probe on a board that has not settled — §06.07.
